1. МЕТА, МЕТОД І МЕЖІ ДОКАЗОВОСТІ

Один предмет аудиту: оцінка поточного коду Android-застосунку, billing backend
та пов'язаного статичного сайту за шістьма критеріями:
технічний борг; Clean Architecture; безпека; надійність; навантаження і межі;
готовність до production. Окремо перевірені кандидати на мертвий код,
дублювання, ускладнення та підтримуваність.

Працювали головний агент і рівно три субагенти:
— архітектура, залежності, залишкові API та дублювання;
— безпека Android і billing backend;
— Android-надійність, accessibility та ресурси пристрою.
Головний агент перевірив серверні обмеження, storage, release/deploy wiring,
сайт, зіставив висновки та створив цей єдиний документ.

Факт: проаналізовано поточне робоче дерево, включно з незакоміченими змінами,
які вже існували до аудиту. На старті було 11 записів git status, з яких
сім modified і чотири untracked. Аудит не обмежувався останнім комітом.

Факт: для всього app/src/main/java виконано статичний аналіз imports,
декларацій і текстових посилань: 118 Kotlin-файлів, 8 029 рядків.
Додатково перевірені посилання шести залишкових API у main/debug/release.
Backend має 12 Kotlin-файлів; перевірені HTTP handlers, auth boundaries,
Google verification, обидва storage adapters, migrations та config.
Детально прочитані цільові execution paths, а не кожна гілка всіх файлів.
Для контролю незмінності зафіксовані SHA-256 185 source/config/public файлів.

Факт: тести та продуктова документація не приймалися за підтвердження
правильної поведінки. Тести не запускалися; тестові джерела використовувалися
лише як місця посилань на залишкові API. Правила .agent прочитані як
керівні інструкції, а не як доказ фактичної архітектури чи працездатності.

Факт: для уточнення default executor і backlog використано офіційний API
контракт JDK 17, відповідного runtime у Dockerfile. Це допоміжне пояснення
семантики бібліотеки; конфігурацію застосунку встановлено з його коду.
Джерело: [Oracle JDK 17 HttpServer](https://docs.oracle.com/en/java/javase/17/docs/api/jdk.httpserver/com/sun/net/httpserver/HttpServer.html#setExecutor(java.util.concurrent.Executor)).

Не виконувалися: build, lint, unit/instrumentation tests, інсталяція APK,
реальна експлуатація вразливостей, звернення до production або Google Play,
навантажувальний прогін, профілювання CPU/RAM/battery, deploy, commit/push.
Ці операції могли б створити додаткові артефакти або змінити середовище.
Секретні файли та фактичні credentials не відкривалися.

Позначення доказів:
Факт — прямо встановлено за source/config.
Висновок — наслідок наведених фактів із зазначеними передумовами.
Недоведено — потрібні runtime, deployment або інші відсутні дані.
Високий — істотний вплив на оплату, основний захист або доступність.
Середній — умовний збій, неповне покриття чи суттєвий борг підтримки.
Низький — локальний залишковий API або обмежене дублювання.
Рівні є оцінкою впливу; це не CVSS і не виміряна частота збоїв.

Скорочення шляхів нижче:
K/ = app/src/main/java/com/shortsblockerkids/
B/ = billing-backend/src/main/kotlin/com/shortsblockerkids/billingbackend/
Шляхи без цих префіксів наведені від кореня репозиторію.

2. ЗАГАЛЬНА ОЦІНКА

Висновок: у коді є змістовна реалізація продукту та придатна основа внутрішніх
архітектурних меж. Водночас готовність до масового production не підтверджена
і за виявленими дефектами не може бути прийнята як завершена.

Критерій                 Оцінка за кодом
Технічний борг           Помірний у Android; суттєвий у серверній обробці
                        запитів, відмов і операційних гарантіях.
Clean Architecture      Внутрішні Android-шари мають правильні залежності.
                        Одні назви папок не були прийняті за доказ.
Безпека                 Незавершена: підтверджено відсутність авторизації
                        запису entitlement за відомим install_id.
Надійність              Часткова: є fail-open, чутливість до wall clock,
                        непрокриті storage failure та event/lifecycle gaps.
Навантаження            Точна місткість невідома. Виявлені послідовна
                        серверна обробка і спільні proxy rate-limit buckets.
Production              Публічний масовий реліз за цим аудитом не готовий
                        до прийняття; працездатність binary не перевірена.

Найсуттєвіші причини оцінки:
— SEC-01: сторонній запит може змінити entitlement відомої інсталяції.
— CAP-01 і SEC-02: один повільний запит або спільна proxy-квота впливають
  на доступність інших користувачів.
— REL-01..03: відкат часу, storage failure і overlay failure порушують
  основний шлях захисту.
— Немає виміряного доказу коректності на живих сторонніх застосунках,
  підтримуваних Android/OEM або під навантаженням.

Недоведено: ні гарантована непрацездатність у кожному звичайному сценарії,
ні гарантована працездатність на всіх пристроях. Статичний аудит встановлює
конкретні дефекти і межі, але не замінює перевірку виконуваного продукту.

4. CLEAN ARCHITECTURE

Факт: повний import scan main Kotlin не знайшов у domain/application
імпортів Android/AndroidX або infrastructure/platform/presentation/
accessibility/core. Application залежить від domain.

Кількість import edges у перевіреному зрізі:
application → domain: 24;
infrastructure → application: 25; infrastructure → domain: 16;
presentation → application: 24; presentation → domain: 17;
platform → application: 12; platform → domain: 18.
Це кількість imports, а не кількість runtime викликів.

Приклади реальних меж:
K/application/port/SettingsStatePort.kt:1;
K/application/port/PinStateStore.kt:1;
K/application/billing/BillingVerificationPort.kt:1;
K/domain/protection/ProtectionEligibilityPolicy.kt:1;
K/infrastructure/storage/DataStoreSettingsStore.kt:1.

Висновок: Android має справжні внутрішні бізнес-шари і зовнішні adapters.
Прямі infrastructure imports у MainActivity відповідають можливій ролі
composition root і самі по собі не доводять порушення залежностей.

Факт: presentation також імпортує domain. Це не зворотна залежність
внутрішнього шару і не автоматичний дефект Clean Architecture.
Висновок: найбільш очевидний борг тут — ручна складність UI state,
а не відсутність усіх архітектурних меж.

Backend не має аналогічної багатошарової структури: невеликий server,
storage interface та зовнішній verifier. Висновок: така компактність сама
по собі не є порушенням. Однак transport, entitlement decisions і I/O
у handlers посилюють наслідки CAP-01 та SEC-01.

Недоведено: повний runtime dependency graph, constructor/service-locator
залежності без imports, всі branch-level контракти й коректність кожного
use case. Хороший import graph не підтверджує працездатність продукту.

5. БЕЗПЕКА

SEC-01. Високий. Заміна entitlement іншої інсталяції за відомим install_id.

Факт: POST verify не автентифікує власника інсталяції:
B/BillingBackendServer.kt:47.
Перевіряються package/product і прив'язка вхідного purchase token:
B/BillingBackendServer.kt:49;
B/BillingBackendServer.kt:52.
Права змінювати вхідний install_id не перевіряються.
Після Google verification record записується:
B/BillingBackendServer.kt:64.

Факт: production PostgreSQL ON CONFLICT(install_id) замінює token hash,
state, activeUntil і verification time:
B/DatabaseMigrator.kt:195.
Verifier повертає EXPIRED для валідної завершеної підписки:
B/GooglePlayDeveloperApiClient.kt:185.

Умова: нападник знає UUID інсталяції жертви та має власний token того самого
package/product, який ще не прив'язаний до іншого запису.
Висновок: UUID жертви + власний завершений token можуть перезаписати
платний entitlement жертви на EXPIRED. Google підтверджує покупку, але
не авторизує зміну саме цього installation record.
Недоведено: спосіб отримання UUID, просте його перебира́ння або фактична
експлуатація. Purchase token жертви і її PIN для описаного шляху не потрібні.

Пов'язане розкриття: GET status повертає entitlement за відомим ID без auth:
B/BillingBackendServer.kt:83;
B/JsonBodies.kt:55.
Android передає ID у query string:
K/infrastructure/billing/HttpBillingVerificationAdapter.kt:51.
Розкриваються стан/строки підписки; purchase token і Google account тут
не повертаються. Потрапляння URL до реальних proxy logs не перевірено.

SEC-02. Високий за спільного reverse proxy. Один peer має квоту всіх клієнтів.

Факт: rate-limit key = endpoint + socket remoteAddress:
B/BillingBackendServer.kt:220.
Gate виконується до handler, а RTDN authentication — всередині handler:
B/BillingBackendServer.kt:143;
B/BillingBackendServer.kt:97.
Невалідні або unauthenticated запити теж збільшують лічильник:
B/RateLimiter.kt:17.

Умова: backend бачить спільну адресу proxy.
Висновок: 30 допущених, навіть некоректних verify-запитів у вікні можуть
зробити наступні легітимні запити 429 до зміни вікна. Аналогічно працюють
status і RTDN; для вичерпання RTDN-квоти JWT пройти не потрібно.
Недоведено: реальна topology. За різних direct IP вплив локалізований
на IP/NAT, а не гарантовано на всіх користувачів.

SEC-03. Високий за доступного origin. Header-based HTTPS gate не є TLS.

Факт: listener — звичайний HttpServer:
B/BillingBackendServer.kt:316.
Програмний HTTPS gate приймає X-Forwarded-Proto=https без перевірки
trusted proxy:
B/BillingBackendServer.kt:210.
Compose публікує port без loopback host restriction:
docker-compose.yml:28.
TLS proxy service або firewall rules цей compose-файл не визначає.

Умова: origin port доступний нападнику або proxy пропускає його header.
Висновок: plaintext HTTP з самостійно заданим header проходить gate.
Production config requireHttps=true не доводить шифрування каналу.
Недоведено: зовнішній firewall/proxy/TLS deployment. Код не доводить,
що origin уже публічно доступний у production.

SEC-04. Середній. Батьківська unlock-сесія зберігається у UI state.

Факт: isUnlocked зберігається/відновлюється rememberSaveable:
K/presentation/app/ShortsBlockerKidsApp.kt:74;
K/presentation/app/ShortsBlockerKidsApp.kt:87.
Coordinator встановлює unlock після PIN та скидає його для explicit disable
і temporary allow:
K/presentation/app/ShortsBlockerKidsCoordinator.kt:92;
K/presentation/app/ShortsBlockerKidsCoordinator.kt:108;
K/presentation/app/ShortsBlockerKidsCoordinator.kt:124.
Callback зміни protected platforms не запускає повторний PIN:
K/presentation/app/ShortsBlockerKidsApp.kt:215.
Перевірений MainActivity.onResume лише refresh-ить state і start-ить billing:
K/MainActivity.kt:199; lifecycle relock у цьому callback відсутній.

Умова: батько передає дитині телефон зі збереженою unlocked Dashboard-сесією.
Висновок: головний disable switch має окремий PIN-flow, але зміна списку
захищених платформ доступна у відкритій сесії. Saved unlock переживає
відновлення UI state. Це локальний ризик сесії, не віддалений bypass.
Недоведено: повна поведінка всіх Compose lifecycle observers і фактичний
restore на пристрої. Сам onResume не доводить відсутність будь-якого іншого
механізму relock поза перевіреним шляхом.

Реальні позитивні security controls:

— Покупка звіряється з Google на fixed HTTPS host, параметри URL-encoded,
  відповідний product шукається у lineItems:
  B/GooglePlayDeveloperApiClient.kt:37;
  B/GooglePlayDeveloperApiClient.kt:132.
  Активна unacknowledged покупка проходить acknowledge:
  B/GooglePlayDeveloperApiClient.kt:49.
— Production вимагає authenticated Pub/Sub configuration:
  B/BackendConfig.kt:133.
  RTDN використовує TokenVerifier, задані audience/issuer/email:
  B/RtdnAuthenticator.kt:28; B/RtdnAuthenticator.kt:32;
  B/RtdnAuthenticator.kt:54.
— SQL значення bind-яться prepared statements. Динамічний whereSql

7.2. Backend: визначальні bottlenecks

CAP-01. Високий. Послідовний default executor + synchronous I/O.

Факт: create не задає setExecutor; handlers синхронно виконують Google/DB:
B/BillingBackendServer.kt:310.
HttpServer default executor використовує thread, створений start(),
за [Oracle JDK 17 HttpServer](https://docs.oracle.com/en/java/javase/17/docs/api/jdk.httpserver/com/sun/net/httpserver/HttpServer.html#setExecutor(java.util.concurrent.Executor)).
Runtime образ — JRE 17:
billing-backend/Dockerfile:1.

Висновок: цей server instance не має налаштованого parallel worker pool.
Повільна verification займає execution path інших запитів, включно з health.
Орієнтир для serial processing: максимальний service rate приблизно 1/T,
де T — середня тривалість handler. Це формула, не benchmark:
T=0,1 s → близько 10 requests/s;
T=1 s → близько 1 request/s;
T=10 s → близько 0,1 request/s.
Реальні T, quotas і запас до saturation невідомі.

Backlog переданий як 0, тобто system default за API, а не доведена
нульова черга і не налаштована місткість:
B/BillingBackendServer.kt:316.

Факт: Google connection має connectTimeout=10 s і readTimeout=10 s:

Slow body/dependency може довго займати serial handler.
Недоведено: JDK/provider/socket defaults, JDBC URL timeout settings і
зовнішні proxy deadlines. Нескінченне зависання кожного запиту не заявлено.

7.3. Явні HTTP quotas

За default config, на один endpoint + socket peer у fixed minute window:

B/BillingBackendServer.kt:219;

За єдиного proxy вони спільні для всіх його клієнтів. За припущення

за цим peer, а не максимум 30 зареєстрованих користувачів.
Фактична доступність може бути нижчою через CAP-01/02.
Fixed windows дозволяють burst біля межі двох хвилин; немає рівномірного

7.5. Формула users і сайт

Для стабільного трафіку потрібні щонайменше:
λ = U × r, де U — активні users, r — requests/user/s;
λ має бути нижчим за виміряну throughput із запасом і нижчим за quotas.
U_max приблизно Q_safe/r — лише модель після вимірювання Q_safe і r.
Тут не відомі ні Q_safe, ні r, ні bursts. DAU/MAU за source не обчислюються.

Сайт генерує static pages:

website/scripts/build.mjs:21.
Application-side website API/database тут немає; deployment CDN/hosting
bandwidth і concurrent visitor capacity не перевірені.
Метрики вимкнені порожнім endpoint:
website/src/config.mjs:11.

через textContent:

Недоведено: походження/свіжість майбутніх metrics. Boolean verified
є перевіркою schema, а не криптографічним підтвердженням реальних подій.
Число сімей/blocked events не прийняте за evidence місткості.

PROD-03. Середній. Shutdown не має підтвердженого graceful drain.
